Core Engine
Data Pipeline Flow
When a dataset is uploaded, a fully autonomous pipeline runs in the background: parse, profile every column, detect issues, compute trust score, check drift, evaluate alerts, and validate contracts.
What happens step-by-step when you upload a file? Deep Dive

Synchronous (before the API responds, <1 second):

  • File extension validated (.csv, .xlsx, .xls, .parquet, .pq)
  • Filename sanitized — path components stripped to prevent directory traversal attacks
  • File streamed to disk in 1 MB chunks. If it exceeds 200 MB mid-stream, the partial file is deleted and a 400 error is returned
  • A Dataset record is created (status: "uploaded")
  • A Job record is created (type: "profile", progress: 0%)
  • An audit log entry records the upload
  • asyncio.create_task() launches the background pipeline — the API response returns immediately

Async background pipeline (runs after user gets the response):

  • 0–10%: Parse file into a Pandas DataFrame (CSV → pd.read_csv(), XLSX → pd.read_excel(), Parquet → pd.read_parquet()). Row/column counts saved.
  • 10–50%: Profile every column — type detection (samples 100 rows), null/unique/duplicate stats, numeric statistics (min/max/mean/median/std_dev), distribution histograms, top values, pattern detection, PII detection.
  • 50–80%: Detection engine runs 4 passes — missing values, duplicate rows, outliers (IQR), type mismatches. Each issue gets severity + repair suggestions with confidence scores.
  • 80–85%: Drift check — saves baseline on first run; on subsequent runs compares against baseline for schema/distribution/volume drift.
  • 85–90%: Trust score calculated across 5 weighted dimensions. Snapshot saved for history.
  • 90–95%: Alert rules evaluated (trust_score_below, issue_count_above, etc.). Emails + webhooks fired if triggered.
  • 95–98%: Data contract validated if one exists (min trust score, max null %, schema check).
  • 98–100%: Lineage nodes created (upload → profile → issues), dataset status set to "profiled", job marked completed.

The user sees the dataset card update from "processing" to "profiled" in real-time as TanStack React Query polls for updates.

What happens when you click "Apply All" repairs? Deep Dive
  • Frontend sends POST /api/datasets/:id/repair with a list of suggestion IDs
  • Backend loads the current dataset file into a Pandas DataFrame
  • For each suggestion, applies the strategy directly to the DataFrame:
    • mean_imputation → df[col].fillna(df[col].mean())
    • median_imputation → df[col].fillna(df[col].median())
    • mode_imputation → df[col].fillna(df[col].mode()[0])
    • deduplicate → df.drop_duplicates()
    • clip_outlier → df[col].clip(lower, upper)
    • coerce_type → pd.to_numeric(df[col], errors='coerce')
  • Repaired DataFrame saved as a new versioned file (e.g., v2.csv). The original file is never modified.
  • DatasetVersion record created with new row count and change summary
  • Issues marked as "resolved"; RepairAction records logged
  • Full pipeline re-runs on the repaired data: re-profile → re-detect → recalculate trust score
  • Lineage graph updated: a "repair" node is added and linked to the issues node
  • Audit log records everything that happened

Key design: Every repair is non-destructive. The original data is preserved, and you can download any previous version.

Why doesn't the trust score reach 100 after repairs? Real Math Example

Example: Titanic dataset (891 rows, 12 columns) after all repairs applied:

Completeness (25%): Formula: 100 - avg_null_pct_across_all_columns

Even after repairing Age and Embarked nulls, the Cabin column still has ~77% nulls (687 out of 891). That's too many to impute meaningfully, so it stays. Average null % across 12 columns ≈ 6.4%. Score ≈ 93.6

Validity (20%): Only counts open type_mismatch issues. After coerce_type repairs, all type issues are resolved. Score = 100 ✓

Consistency (20%): Only counts open outlier + duplicate issues. After deduplicate + clip repairs, these are resolved. Score = 100 ✓

Uniqueness (20%): This is the key dimension. It measures duplicate values within each column across column profiles — not detected issues. A "Sex" column with 2 values across 891 rows has ~889 "duplicates". Same for "Embarked" (3 values), "Pclass" (3 values), "Survived" (2 values). This is natural for categorical data, but the formula still penalizes it. Score ≈ 85–92

Integrity (15%): No custom quality rules defined → no violations. Score = 100 ✓

Overall = (93.6 × 0.25) + (100 × 0.20) + (100 × 0.20) + (88 × 0.20) + (100 × 0.15) = 23.4 + 20.0 + 20.0 + 17.6 + 15.0 = 96.0

Bottom line: A score of 95–97 after repairs is excellent. A perfect 100 would require zero nulls in every column AND zero repeated values — which doesn't exist in real-world data. The score is honest by design.

How does each import method work under the hood? Deep Dive

File Upload:

  • Frontend validates extension + size before sending
  • Sent as multipart/form-data to POST /api/datasets/upload
  • Backend sanitizes filename (strips path to prevent ../../etc/passwd attacks)
  • Streamed to uploads/{dataset_id}/{filename} in 1 MB chunks
  • If file exceeds 200 MB mid-stream, partial file is deleted and 400 returned

URL Import:

  • httpx.AsyncClient with follow_redirects=True and 60s timeout
  • File type detected by URL extension: .parquet/.pq → Parquet, .xlsx/.xls → Excel, else → CSV
  • Also checks Content-Type header for Excel (spreadsheetml)
  • Entire response loaded into memory, parsed by appropriate Pandas reader
  • Saved as data.csv in the uploads directory, then pipeline runs

Google Sheets:

  • Extracts spreadsheet ID from URL via regex: /spreadsheets/d/([a-zA-Z0-9_-]+)/
  • Extracts gid parameter if present (defaults to 0 = first tab)
  • Constructs export URL: https://docs.google.com/spreadsheets/d/{ID}/export?format=csv&gid={GID}
  • Downloads using the same URL import function

PostgreSQL:

  • Connects via asyncpg.connect("postgresql://user:pass@host:port/db")
  • Runs conn.fetch(query) — returns rows as Record objects
  • Each row converted to dict, assembled into a DataFrame
  • Default query template includes LIMIT 10000 as safety

All 4 methods converge: The DataFrame is saved as CSV → Dataset record created → Background pipeline runs (profile → detect → score → drift → alerts). Same pipeline regardless of data source.

Security
Authentication & Authorization
JWT-based auth with bcrypt password hashing and role-based access control across three tiers.
How does JWT authentication work in detail? Deep Dive

Signup flow:

  • Client sends POST /api/auth/signup with email, password (min 8 chars), full_name
  • Password is hashed with bcrypt — a one-way hash with automatic salt. Even if the database is stolen, passwords can't be reversed
  • First user ever to sign up is auto-promoted to admin. All subsequent users get analyst role
  • A JWT is created: {sub: user_id, email: "...", role: "analyst", exp: now+72h}, signed with HS256

Login flow:

  • Client sends email + password → backend looks up user → bcrypt.verify(password, hashed)
  • If valid, new JWT issued (72-hour expiry). Returned to frontend.

Request authentication:

  • Frontend stores token in localStorage and attaches it as Authorization: Bearer <token> on every request via Axios interceptor
  • Backend get_current_user() dependency decodes the token, looks up the user in the database, and verifies they exist and are active
  • If token is expired/invalid/user disabled → HTTP 401

Why router-level auth? Instead of decorating each endpoint individually (error-prone — you might forget one), auth is applied when registering routers on the FastAPI app. Public routers (health, auth) mount without guards. All 14 protected routers receive dependencies=[Depends(get_current_user)] at registration time. This makes it impossible to accidentally expose an unprotected endpoint.

Engine Detail
Detection & Repair Strategies

Issue Detection (4 passes)

Missing Values

Per-column null count and percentage. Severity: critical (>30%), warning (>5%), info (any). Suggests mean/median/mode imputation or row drop.

Duplicate Rows

Exact full-row match detection. Severity: warning (<10% of rows) or critical. Suggests deduplication keeping first occurrence.

Outliers

IQR method on numeric columns (requires ≥10 values). Values below Q1−1.5×IQR or above Q3+1.5×IQR flagged as warning. Suggests clip or remove.

Type Mismatches

Columns that are >50% numeric but contain non-numeric values (<30% of sample). Flagged as warning. Suggests coerce to numeric with NaN replacement.

How does each detection algorithm work? Algorithm Detail

Missing Values — per column:

  • Count nulls via df[col].isna().sum()
  • Calculate percentage: null_count / total_rows × 100
  • Severity thresholds: >30% = critical, >5% = warning, any = info
  • Stores first 50 affected row indices for the UI to highlight
  • For numeric columns: generates mean + median imputation suggestions (median is recommended — more robust to outliers)
  • For non-numeric: generates mode imputation (fill with most common value)
  • Always offers drop_rows as a last resort (lowest confidence at 0.50)

Duplicate Rows — dataset-wide:

  • Uses df.duplicated(keep=False) — marks ALL copies of duplicate rows, not just the second one
  • If ≥10% of rows are duplicates → critical severity
  • Deduplication keeps first occurrence: df.drop_duplicates() with confidence 0.95

Outliers — IQR method, per numeric column:

  • Requires ≥10 non-null values to run (avoids false positives on tiny samples)
  • Q1 = 25th percentile, Q3 = 75th percentile, IQR = Q3 − Q1
  • Lower bound = Q1 − 1.5 × IQR, Upper bound = Q3 + 1.5 × IQR
  • Values outside these bounds flagged as outliers
  • Clip suggestion: df[col].clip(lower, upper) — values are clamped to the bounds
  • Remove suggestion: delete rows with outliers entirely (lower confidence)

Type Mismatches — per column, sample-based:

  • Samples 200 values from each non-numeric column
  • Tries parsing each as float (handling commas, whitespace)
  • If >50% parse as numeric BUT some don't (<30% failures) → mixed-type column
  • Example: a "price" column with ["10", "20", "N/A", "30"] — mostly numeric but "N/A" breaks it
  • Coerce suggestion: pd.to_numeric(df[col], errors='coerce') — non-parseable values become NaN
How does the AI integration (Gemini) work? Deep Dive

The app uses Google Gemini 1.5 Flash (fast, cost-effective LLM) for 4 features:

  • AI Dataset Summary — sends column profiles + issues to Gemini, asks for an executive-level data quality assessment. Returns plain-English summary with recommendations.
  • Issue Explanations — for each detected issue, asks Gemini to explain it to a business analyst, including potential business impact.
  • Natural Language Commands — you type "fill missing ages with median" and Gemini parses it into a structured action {strategy: "median_imputation", column: "Age"}. A regex fallback parser handles common patterns if the API is down.
  • Cleaning Code Export — generates reproducible pandas code for all applied repairs. Copy into a Jupyter notebook to replicate the exact pipeline.

Every AI feature has a hardcoded fallback. If the Gemini API key isn't configured or the API is unavailable, features return sensible defaults instead of crashing. This is critical for the free-tier deployment.

Anticipated Questions & Answers
Click to expand answers for questions you might get during the presentation.
"What makes this different from just running pandas scripts?"

Pandas is a library — you still need to write the profiling code, detection logic, repair strategies, scoring formula, and build a UI. CleanOps AI is a platform that does all of that autonomously, tracks version history, monitors for drift over time, and integrates into CI/CD pipelines through a quality gate API. It's the difference between writing individual SQL queries and using a database management tool.

"How does this scale with larger datasets?"

The processing engine uses Pandas, so it's limited by server memory — roughly datasets up to a few million rows on standard hardware. On Render free tier (512 MB RAM), it handles ~500K rows comfortably. For production scale, the profiling and detection services are modular — they could be swapped to use Spark, DuckDB, or Polars without changing the API layer or the frontend. The architecture separates the computation engine from the platform logic.

"Why SQLite instead of PostgreSQL?"

SQLite is used for zero-configuration development — no database server needed, the database is just a file. The database URL is a single environment variable (DATABASE_URL). Change it to a PostgreSQL connection string and everything works because SQLAlchemy abstracts the entire database layer. The same ORM models, same queries, same migrations work on both engines. This is a deliberate architecture choice: database-agnostic by design.

"Why not use Great Expectations or dbt tests?"

Great Expectations and dbt are rule-based testing frameworks — you write the rules (expectations/tests), and they check data against those rules. CleanOps AI auto-detects issues without any configuration. Upload a file and it finds missing values, duplicates, outliers, and type problems automatically. It also provides auto-repair, trust scoring, AI explanations, drift monitoring, and a full visual UI. GE is a library; CleanOps AI is a platform.

"What about real-time streaming data?"

The current architecture handles batch data — file uploads and scheduled scans. For streaming, you'd add a Kafka or Redis queue consumer that triggers the pipeline on new data arrival. The pipeline itself is already async and could process micro-batches. The scheduled scan infrastructure (which already runs the full pipeline on a timer) is the foundation — extending it to event-driven triggers is a natural next step.

"Is the data secure?"

Multiple layers of security:

  • Passwords: bcrypt hashing with automatic salt — one-way, not reversible
  • Authentication: JWT tokens with 72-hour expiry, required on every protected endpoint
  • Authorization: Role-based access (admin/analyst/viewer) enforced at the router level
  • File security: Filename sanitization prevents path traversal attacks
  • API validation: Pydantic validates every request body, query parameter, and path parameter
  • CORS: Configurable allowed origins
  • Webhooks: HMAC-SHA256 signed so receivers can verify authenticity
